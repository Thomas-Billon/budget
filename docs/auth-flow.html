The shared promise only covers one JS context. Two tabs each hold their own _refreshPromise but share the same cookie. If they refresh at the same time, the second one presents an already-rotated token — the scenario detailed in the next tab.
The replayed call carries canRetryOnUnauthorized: false. A second 401 is therefore handed back to the caller instead of triggering another refresh — that is what guarantees no loop.

Rotation, theft, and the race between tabs

Every refresh consumes the token and issues a new one. A token presented twice is therefore suspicious — unless it is plain concurrency, which is what the grace period is for.

Without the grace period, t3 is read as a stolen token being replayed: every token of the user is revoked and they are signed out of all their devices — for the sole crime of having two tabs open.
Accepted trade-off: for a few seconds after a rotation, reuse detection is deliberately relaxed so that legitimate concurrency isn't punished. The window is kept as short as possible, and a stolen cookie compromises the account through the normal path anyway.

Authentication journeys

The four paths through which a session can be born or reborn. All of them converge on IssueTokensAsync, the only place that ever issues a token pair.

Registration

Create an account — without opening a session
  1. User created
    Password rules enforced by Identity
  2. Confirmation email sent
    Link valid 24h, built from AppUrl
  3. No token issued
    Signing in stays impossible until the email is confirmed

Email confirmation

Activate the account from the emailed link
  1. Link opened
    Public route /confirm-email — email and token in the query
  2. Token validated
    Identity token with its own lifetime
  3. Redirect to sign-in
    Still no session open at this point

Sign-in

The only path that opens a session
  1. Password checked
    Locked out for 1h after 3 failures
  2. Confirmed email checked
    Silent refusal otherwise
  3. Token pair issued
    JWT in the response, refresh token in the cookie
  4. JWT decoded client-side
    The displayed profile comes from the claims, not an extra call

Forgotten password

Regain control of the account
  1. Reset requested
    Same response whether the account exists or not
  2. Link sent
    Valid 1h
  3. Password reset
    Every existing session is revoked
An unconfirmed email and a missing account both return null, so the client sees the same error. This is deliberate: telling them apart would let anyone enumerate existing accounts. Same reasoning behind the silent forgotten-password send.
